# Project Overview

**Strava Running Bot** is a Node.js Discord bot that posts Strava activities from running team members to a Discord channel in real time. It also manages team races (planning, weekly/monthly announcements) and personal bests.

Single-process app: an HTTP webhook server (Strava events + OAuth callback) plus a Discord client running in the same process.

# Architecture

## Flow

1. Member runs `/register` in Discord → bot returns Strava OAuth URL.
2. Member authorizes → Strava redirects to `/auth/strava/callback` → tokens are AES-256 encrypted and persisted via `DatabaseMemberManager`.
3. Strava sends activity events to `POST /webhook/strava`.
4. `ActivityProcessor` fetches the full activity via `strava/api.js` (refreshing tokens as needed), formats it through `EmbedBuilder`, and posts to the configured Discord channel.
5. `Scheduler` (node-cron) fires weekly/monthly race announcements via `RaceManager`.

## Module conventions

- One class per file; filename matches class name (e.g. `MemberManager.js` → `class MemberManager`).
- Managers own state + persistence for a single domain concept (members, races, PBs, settings).
- Utils are stateless helpers.
- Logger is the only allowed I/O wrapper — do not `console.log` in `src/`.
- All Strava token access goes through `strava/api.js`; never call Strava endpoints directly elsewhere.
- All encrypted-at-rest fields go through `utils/EncryptionUtils.js`.

## Database

- SQLite file at `config.database.path` (default `/app/data/bot.db` in Docker, override locally via `DATABASE_PATH`).
- Schema in `src/database/schema.js`; migrations generated by `npm run db:generate`, applied by `npm run db:migrate`.
- `DatabaseManager` is the connection/lifecycle owner; per-domain managers wrap it.

# Deployment

## Local development

```
cp .env.example .env        # fill in DISCORD_*, STRAVA_*, ENCRYPTION_KEY
npm install
npm run db:migrate
npm run dev
```

`PORT` defaults to 3000. Strava webhooks require a public URL — use a tunnel (ngrok, cloudflared) and register the webhook via `utils/setup.js`.

## Docker

```
docker compose up -d        # uses docker-compose.yml
```

Production compose file: `docker-compose.prod.yml`. Image is built and pushed by `.github/workflows/build-and-push.yml`.

# Versioning

Releases are automated by **release-please** — never bump `package.json`, write
`CHANGELOG.md`, or create a `v*` tag by hand. All three are generated.

## How a release happens

1. PRs merge to `main` (squash merge — **the PR title becomes the commit subject**).
2. release-please reads those subjects and keeps a `chore(release): x.y.z` PR
   open with the version bump + changelog.
3. Merging that PR creates the `vX.Y.Z` tag and GitHub Release, and the same
   workflow run then builds the versioned image (`:X.Y.Z`, `:X.Y`).

`:latest` still tracks `main`, so merges deploy without waiting for a release.

## Commit type → version bump

| Type | Bump | In changelog |
|------|------|--------------|
| `feat` | minor (1.0.0 → 1.1.0) | Features |
| `fix` | patch (1.0.0 → 1.0.1) | Bug Fixes |
| `perf` | patch | Performance |
| `revert` | patch | Reverts |
| `docs` `chore` `ci` `test` `refactor` `build` `style` `deps` `deps-dev` `docker` | none | hidden |
| `feat!` / `fix!` / `BREAKING CHANGE:` footer | **major** (1.0.0 → 2.0.0) | Breaking |

## Rules

- **Pick the type deliberately** — it decides the version users get. A
  user-visible behaviour change is `feat` or `fix`, never `chore`.
- **A `!` or `BREAKING CHANGE:` footer publishes a major.** Only use it for a
  genuine break (config/env change, data migration that can't roll back, a
  removed command). Say what breaks and what to do about it.
- **The PR title must be a valid conventional subject** — CI (`PR Title`)
  enforces it. It is the only text release-please ever reads, so a bad title
  means no changelog entry and no bump, silently.
- Never edit `.release-please-manifest.json` by hand; release-please owns it.
- The versioned image is built by the `publish-image` job **inside**
  `release-please.yml`, not by a tag push. GitHub won't start a workflow from an
  event raised by `GITHUB_TOKEN`, so `on: push: tags:` never fires for a
  bot-created tag. Don't "fix" this by adding a tag trigger — it will silently
  never run.
- `config.app.version` reads `package.json`, so `/botstatus` and `/health`
  report the running version automatically. Don't hardcode a version anywhere.
